# 09. POC2 설계 보완 브리핑 — T3Q 구축 방향 반영용

> **목적**: 별도로 작성 중인 POC2 설계 문서(거의 완성 단계)를, 주관기관 T3Q가 실제 구축 중인
> 데이터 메타·온톨로지 방향과 대조해 **보완**하기 위한 참고 자료다.
> POC1과는 무관하다(POC2는 처음부터 다른 컨셉으로 새로 설계됨). 이 문서는 아무것도 강제하지
> 않으며, 반영 여부는 설계자가 판단한다. 출처: 2026-07-30 T3Q 테스트 사이트 조회(상세: docs/08).
> **주의: T3Q 사이트는 데이터 구축 중의 테스트 모듈이며, 아래 규격은 확정이 아니다.**

## 1. T3Q 구축 방향 요약

### 1.1 구축 파이프라인
`원시 수집(파일/DB) → 문제유형정의(스키마 수집·문서 md 변환·역량질의 정의·응용온톨로지 스키마 생성) → 온톨로지 인스턴스 구축(변환 Agent 실행 → Passage 인스턴스)`
- **모든 데이터의 최종 단위가 "Passage"다.** 비정형 문서만이 아니라 정형 DB 행·테이블 정의·재난문자까지 SchemaType별 Passage 인스턴스로 수렴한다 — RAG 검색을 전제로 한 설계.
- 인스턴스 생성은 "변환 Agent"(SchemaType별 템플릿 설정→실행→로그) 단위로 관리되고, 내부 도구가 `sheet_passage_extract`·`extract_sheet_from_search`·`extract_sheet_from_sql` 같은 도구(tool) 명명 규약을 따른다(MCP 도구화의 전 단계로 해석됨). 대외 MCP/RAG API는 아직 미노출.

### 1.2 사건 중심(Event-Centric) 허브 온톨로지
- 허브 = **DisasterEventMasterPassage**(재난사건 Master): EventIdentity(사건ID·유형·지역·순번·상태) / Time / Location(법정동코드 10자리·WGS84) / Damage(사망·실종·부상·공공·사유·농작물·기반시설) / CrisisLevel / RiskFactors
- 도메인 스키마 45종(상황경보·문서보고·피해복구·취약지역·잠재위험요소·기상수문환경·영상GeoAI·공간기준·해외참조·정책표준참조)이 **`RefDisasterEventID`로 Master를 역참조**한다(Master는 하위 목록을 갖지 않음).
- **EVENT_ID 생성 규칙**: `{YYYYMMDD}-{DisasterTypeCode}-{RegionCode 5자리}-{순번 3자리}`, 정식 표기 `EVT::20240715-FLOOD-44210-001`. EventStatus: 발생·진행·종료·보정·병합.
- 스키마 간 연결 유형: ref_event(사건 역참조)·spatial(법정동·좌표 공간 연결)·references·type_match(유형 적용)·relates_to·derived(**해외사례→Master "유사사례"**)·code_ref(용어·SOP).

### 1.3 표준 코드 체계 (Controlled Vocabulary 9종)
| 코드계 | 값 |
|---|---|
| disaster_type(간이) | 자연: FLOOD(홍수·침수)·TYPH(태풍·호우)·QUAKE·SLOPE(산사태·붕괴)·FIRE(산불)·SNOW / 사회: FIRE_S·CHEM·BIO |
| crisis_level | LVL_01 관심 · LVL_02 주의 · LVL_03 경계 · LVL_04 심각 |
| damage_scale | DMG_DEATH/MISS/INJ(명), DMG_PUB/PVT/AGR(백만원), DMG_INFRA |
| risk_factor | rain_fall(시간당)·rain·precipitation(누적)·wind·slope·river_level·tide·temperature |
| observation_source | MET_AWS·MET_ASOS(기상관측), SAT_SAR·SAT_OPT(위성), GIS_ADM·GIS_HAZ·GIS_VULN |
| sop_stage / doc_type | S01~S05 / DOC_DAMAGE·RESPONSE·SITUATION·LOG |
| propagation_channel | CBS_EMG·CBS_DIS(공식)·MEDIA_*·SNS_* + 신뢰등급 |
| ai_analysis_type | AI_SUM(요약)·AI_PRED(피해예측)·**AI_SIM(유사사례)**·AI_SOP·AI_EVAL·AI_IMG |

### 1.4 재난유형 T코드 택사노미
- 표준 **TTAK.KO-10.1047** 기반 3단 분류 77노드가 온톨로지에 공식 탑재. prefix 매칭(부모 T1·T101 선택 시 하위 자동 포함).
- 자연재난 T1: 기상 T101(T10105 태풍·T10106 풍수해·T10107 호우 등 8종), 수문 T102(T10206 홍수 등 6종), 기후 T103, 지질 T104(T10401 산사태 등), 천문 T105 / 사회재난 T2: 화재·폭발 T201, 붕괴 T202(급경사지·댐), 교통 T203, 화생방 T204, 환경오염 T205 등.
- 사건 속성에는 간이 코드(FLOOD 등), 분류·필터에는 T코드를 쓰는 **이중 체계**. 모든 SchemaType에 taxonomyCodes가 태깅됨.

### 1.5 근거 계보(lineage)와 대표 데이터
- 정형 DB(전국 자연재해위험지구 14,921건 — 저감계획 시도 입력 DB가 원천) 각 행에 원본 엑셀 **파일 경로·시트명·행번호** lineage가 JSON으로 부착됨. 근거 추적이 정형 데이터까지 기본값.
- **홍수취약지구 관리카드 249건**이 인스턴스 구축 최선행(하천별 PDF 1건=Passage 1건): 일반현황 / 취약 상세 / **RiverPlan(측점·계획홍수량·계획홍수위·제방고·고시일)** / 피해이력·점검 / 대책·비상연락망 / **FloodRiskSystem(취약지구 대응수위·참조관측소(관측소명·대응수위·거리)·정보전달체계(1단계 주의보/2단계 경보 제공수위·SMS/CBS))**
- NDMS(행안부 국가재난관리시스템) 22개 시스템 테이블정의서를 수집해 FieldPassage 66,885건·TablePassage 4,885건으로 인스턴스화 — 기존 실계 스키마와의 정합을 데이터로 확보. 긴급재난문자 4,802건 인스턴스화.

### 1.6 역량질의(CQ)와 커버리지
- 정의된 문제유형: "AI 기반 자연재난(태풍·호우) 대응 지원 서비스 구축 및 실증" — CQ 5문:
  ①군내 어떤 하천이 범람 위험인가 ②저지대 침수 위험 지역은 어디인가 ③급경사지 산사태 위험 지역은 어디인가 ④어떤 수위계/우량계를 모니터링해야 하는가 ⑤과거 침수지역은 어디인가
- 원시 코퍼스: 소하천정비종합계획 전국 시군구 단위 적재(강원~충북, 인제·영천·의왕·구미 포함 / 남원·부산 없음), 홍수취약지구 249, 침수흔적도·재해연보·중대본 보고서 등. **자연재해저감종합계획·하천기본계획의 비정형 본문은 미착수(폴더만 존재)**.
- RAG 해결 방식 예시(T3Q 문서 명시): 키워드→Master 검색→도메인 Passage를 RefDisasterEventID로 조회→LLM이 EVT ID를 인용해 답변. 관리카드형은 "단일 Passage 내 N-Depth 구조로 복합 질문을 한 번의 검색으로 해결".

## 2. 설계 점검 체크리스트 (강제 아님 — 정합 관점의 대조 항목)

1. **사건 식별**: 설계의 사건/상황 ID가 T3Q EVENT_ID 4요소(일자·유형·행정코드·순번)와 호환되는가(형식이 달라도 변환 가능하면 충분)
2. **재난 분류**: T코드 택사노미(3단·prefix)를 수용하거나 매핑표를 갖는가. 간이 코드(T3Q FLOOD가 "홍수·침수" 포괄)와의 세분화 차이를 인지하는가
3. **코드 체계**: 위기경보 4단계(관심/주의/경계/심각), risk_factor(rain_fall·river_level 등), 실시간 관측 연동 시 observation_source(MET_AWS 등) 코드와 용어 충돌이 없는가
4. **데이터 단위**: 검색·근거의 기본 단위가 Passage 개념과 대응되는가, 원본 추적(lineage — 파일·시트·행 또는 문서·장·쪽)이 설계에 있는가
5. **하천·관측**: 하천 위험 정보가 FloodRiskSystem 구조(참조관측소, 단계별 기준수위/제공수위)와 필드 수준에서 정렬 가능한가
6. **질의 시나리오**: CQ 5문에 답할 수 있는 설계인가(하천 범람·저지대 침수·산사태·모니터링 지점·과거 침수)
7. **유사사례**: AI_SIM이 T3Q 표준 분석유형이자 온톨로지 관계로 존재함을 활용하는가

## 3. ChatGPT 보완 요청 프롬프트 (그대로 복사)

> 첨부한 「T3Q 구축 방향 요약」(docs/09)과 상세 분석(docs/08)은 주관기관이 실제 구축 중인 데이터 메타·온톨로지 내용이다(테스트 단계이며 확정 규격 아님). 지금까지 작성한 POC2 설계 문서를 이 내용과 대조해 보완하라.
>
> 1) 설계 문서를 항목별로 점검해, docs/09 2장 체크리스트 7개 기준으로 **정합 / 부분정합 / 무관**을 판정하고 근거를 제시하라.
> 2) 보완이 필요한 항목은 설계 문서의 해당 절을 지목하고 **수정 문안**을 직접 제시하라.
> 3) T3Q 방향과 다르게 가는 항목은 그것이 의도적 차별화인지 나에게 **확인 질문**으로 남겨라.
>
> 기존 설계의 컨셉과 구조는 유지한다 — T3Q 내용을 이유로 설계를 갈아엎지 말고, 용어·코드·식별자·인터페이스 수준의 정합 보완에 집중하라. 판정과 수정 문안에서 T3Q 수치·코드는 첨부 문서의 값만 사용하고 임의로 만들지 마라.
