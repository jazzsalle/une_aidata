# ADR-018 T3Q LLM 대화구조 — 이력 정본은 UNE 보유, 맥락 전달은 T3Q 멀티턴 세션

## Status
Accepted (2026-08-22 사용자 결정)

## Context

상황입력→적용→AI Agent 대화 흐름에서 T3Q LLM API 를 연계할 때 상황정보와 대화맥락을
어떻게 전달할지 결정이 필요했다.

현재 구조는 무상태다 — 매 질문의 요청 본문에 CurrentSituation 전체가 실리고
(`SituationAgentPanel.tsx` → `apiClient.ts` POST `/api/v1/agent/messages`
body `{situation, message, context}`), 서버(`server/domain/agent.ts`)는 요청 간 아무것도
저장하지 않는다. 대화 이력(질문·답변·⟳상황갱신 시스템 턴)은 서버로 전송되지 않고 화면
스레드(AgentTurn[]) 상태로만 존재한다.

T3Q 측은 멀티턴(세션 기반 대화)을 지원한다고 확인해 주었다. 이에 따라 "대화이력을 누가
들고 갈 것인가"와 "맥락을 T3Q 에 어떤 수단으로 전달할 것인가"를 분리해 결정한다.

## Decision

1. **대화이력의 정본은 UNE 측이 보유한다.** 질문·답변·⟳상황갱신 시스템 턴을 포함한
   스레드가 감사·재현의 근거이며, "이 판단이 어느 조건에서 나왔는가"를 요청 단위로
   되짚는 출처다. T3Q 세션은 이 정본의 사본·전달 수단일 뿐이다.
2. **T3Q LLM 맥락 전달은 T3Q 멀티턴 세션을 활용한다.** 대화 시작 시 상황정보로 세션을
   열고, 이후 턴은 질문과 세션 식별자만 전달한다 — 매 턴 상황·이력 전체를 재전송하지
   않아 토큰·전송량을 최소화한다.
3. **상황(조건) 갱신 시 세션에 새 상황정보를 재주입한다.** 적용·재산정(⚙ 조건 제안 →
   지금 적용하고 질문) 흐름에서 조건 변경 전후 비교가 한 대화 안에서 이어지는 현
   UX 를 유지한다. 재주입 시점은 화면의 ⟳ 시스템 턴과 일치시킨다.
4. **세션 유실·만료 복구 경로를 어댑터에 둔다.** 세션이 끊기면 어댑터가 UNE 보유
   이력(최근 N턴 + 현재 상황)으로 세션을 재구성한다. 재구성 실패는 연계별 Fallback
   (현 rule/Seed 답변)으로 처리하며 서비스 전체 오류로 만들지 않는다(v0.7 규칙 7).
5. **T3Q 종속 사항은 `server/providers` 어댑터 내부에 격리한다**(CLAUDE.md 규칙 2) —
   세션 식별자 형식·만료정책·재주입 규약·상황→프롬프트 변환 전부. 세션ID 는 화면에
   노출하지 않는다.
6. **실 API 계약 수신 전에는 구현하지 않는다.** T3Q LLM 연계는 pending 을 유지하고
   (ADR-015·017 의 Mock 우선 원칙), 우리 쪽 계약 변경(예: AgentMessageRequest 에
   history 필드)이 필요해지면 그 시점에 영향범위 보고 후 승인 절차를 밟는다.

## Consequences

- 매 턴 전송량·토큰이 최소화되고, 턴 수가 늘어도 요청 크기가 자라지 않는다.
- 이력(UNE 정본)과 세션(T3Q 사본)의 이중화로 세션 유실에 내성이 생긴다 — 복구는
  언제나 우리 이력에서 출발한다.
- 어댑터가 세션 수명주기(생성·재주입·만료·재구성)를 관리하는 부담을 진다.
- T3Q 계약 협의에서 요구할 항목이 명확해진다: 세션 생성/종료 API · 세션 만료 정책 ·
  상황정보 재주입 방식 · 세션 복구(이력 일괄 주입) 지원 여부.
- 화면·기존 무상태 계약은 당장 변경이 없다 — 스레드 상태가 이미 정본 역할을 하고 있다.
