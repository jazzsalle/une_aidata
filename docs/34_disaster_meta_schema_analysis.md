# 원시데이터 목록·재난 메타 스키마 데이터(260813) 분석

> 대상: `GIS_data/25. ★원시데이터 목록 및 재난 메타 스키마 데이터_260813/` (2026-08-13 전달분)
> 작성: 2026-08-20 · 재난안전 AI 대응지원 POC 개발측
> 판단 요지: **이 자료는 "화면 표출 항목" 그 자체가 아니라, 화면에 표출할 값이 어떤 메타 체계로
> 오는지를 정의한 상류 규격이다.** 화면 표출에 직접 닿는 것은 인스턴스의 `passage`(근거 문장)와
> 역량질문(CQ), 그리고 계약 필드(사건ID·재난유형코드·행정구역코드)다.

## 1. 이 폴더가 무엇인가 — 한 장 요약

NIA 「재난안전 AI데이터 구축」(RFP 2026.3) 사업의 원시데이터 정비측(T3Q)이 만든
**메타데이터 체계 패키지**다. 네 덩어리로 구성된다.

| 구성물 | 내용 | 규모 |
|---|---|---|
| ① 원시데이터현황 V0.4 | 수집 원시데이터 전체 목록 + 수집 경로 + 미수집 NDMS 테이블 | 265건 목록 · 4시트 |
| ② 재난메타 정의서 v0.96 | 층위별 메타데이터 요소 정의(TTA 표준 기반) — 전체 체계의 규범 | 고유 요소 300 · 13시트 |
| ③ 데이터셋 규격 3종 v0.8 | CCTV·드론·위성 AI 학습데이터셋의 GeoJSON 페이로드 + DCAT 래퍼 | 각 12시트 |
| ④ 계획보고서 메타스키마·인스턴스 | 자연재해저감·하천기본·소하천정비 3종 보고서의 구조 스키마와 추출 인스턴스 | 인스턴스 123,070건 |

한 문장으로: **"원시데이터가 무엇이 있고(①), 그것을 어떤 공통 언어로 기술하며(②), AI 학습용
데이터셋은 어떤 포장으로 나가고(③), 계획보고서 문서는 어떻게 구조화·추출되는가(④)"** 를 정한
문서군이다.

우리 리포가 이미 갖고 있던 `재난메타_정의서_v0.6`(메타데이터 참고자료(T3Q)/)의 **후속 갱신본
(v0.96)** 이 포함되어 있다 — v0.6 기준으로 잡아 둔 우리 T3Q Adapter 계약의 대조 대상이다.

### ③ CCTV·드론·위성 GEOJSON DATASET v0.8 — AI 학습셋 포장 규격

세 파일이 같은 틀이다: `Dataset → Group → Item(영상/이미지) → Feature(GeoJSON) → Properties`
계층의 페이로드 스키마 + **DCAT 3.0 카탈로그 래퍼** + **AI 패키징 메타**(NIA AI Ready 가이드).

- 페이로드 루트에 `disaster_type_code`(T코드)·`event_datetime`·`crs`(EPSG:4326) 필수
- `about_event` 블록으로 사건 마스터ID(`event_master_id`) 결합 — GLIDE 번호는 선택
- 형식이 여러 개면 `distribution[]` 로 분리(원본 GeoTIFF·타일 PNG·GeoJSON 라벨 등)
- AI 패키징: 수집목적·구성개요·인스턴스수·전처리·라벨스키마·출처기관 등 (AID-xx)
- 재난유형별 페이로드 예시 5종(홍수·풍수해·호우·산사태·태풍) 동봉

### ④ 계획보고서 3종 메타스키마·인스턴스 — 문서를 데이터로

보고서 유형마다 4계열 산출물이 있다.

| 산출물 | 내용 |
|---|---|
| 메타상세(json/yaml) | 문서군 전체의 DCAT 서술 + **형식구조**(장·절·표 트리) + **의미구조**(업무 객체 트리) + 둘 사이 매핑 + 품질 실측 |
| 메타스키마(html) | 위를 사람이 보는 형태로 |
| 인스턴스_형식구조 | 실제 문서의 장·절 단위 인스턴스 |
| 인스턴스_의미구조 | **표·본문에서 추출한 업무 데이터 인스턴스** — 본체 |
| 역량질문(CQ) | 이 자료가 답해야 하는 질문 11개씩 |

인스턴스 규모와 표본(중요 — 표본 지역이 우리 대상지역이 아니다):

| 보고서 | 표본 | 인스턴스 | 주요 클래스 |
|---|---|---:|---|
| 자연재해저감종합계획 | **대구광역시 2016** (스키마는 16세트 194파일에서 유도) | 19,996 | 위험지구·저감대책·피해이력 |
| 하천기본계획 | **동진강 2017** | 17,075 | 홍수조절분석 14,877 · 하천환경 1,196 · 시설 |
| 소하천정비종합계획 | **경남 김해** | 85,999 | 소하천 조서·시설·홍수량 |

인스턴스 한 건의 구조가 화면 표출과 직결된다:

```json
{
  "@type": "urn:rawdata:class/river-environment-analysis",
  "instance_kind": "measurement",
  "measured_property": "...", "value": 25.0, "unit": "등급",
  "answers_cq": ["CQ-AX-OBJ-01"],
  "passage": {
    "passage_text": "동진강 SS(㎎/L)의 기준은 25 등급이다. 출처: …(27쪽).",
    "embedding_target": true,
    "filter_meta": { "type_name": "...", "class_iri": "...", "cq_ids": [...], "set_id": "set-01" }
  },
  "keys": { "domain": { "river_name": "동진강" } },
  "prov:wasDerivedFrom": { "source_file": "...", "page": 27 }
}
```

즉 **모든 값이 근거 문장(passage)과 출처(파일·쪽)를 달고 온다.** `search_index_hint` 에
벡터 대상 필드·필터 필드까지 지정되어 있어, 이것이 T3Q 검색(RAG)이 돌려줄 페이로드의
원형임을 말해 준다.

역량질문(CQ) 11개씩은 화면이 답해야 하는 질문 목록으로 읽힌다. 예(하천기본계획):
"각 계획 구간의 빈도별 계획홍수량과 계획홍수위는 얼마이며, 제방 여유고가 설계기준을
충족하는가?" — 우리 계획·근거 패널이 rivers.json 으로 이미 표출하는 바로 그 항목이다.

## 3. "화면 표출 항목 메타데이터" 판단에 대한 검토

절반은 맞고, 절반은 더 크다.

**맞는 부분** — 화면 표출에 직접 닿는 것:

- 인스턴스의 `passage` = 화면의 **근거 문장**(우리 유사사례 evidence·계획근거 패널과 같은 자리)
- `answers_cq` = 값이 **어느 화면 질문에 속하는지**의 분류 — 화면 섹션 배치 기준으로 쓸 수 있다
- 위험지구 레코드 규칙("위험지구 1건 = 레코드 1건, 키 = 지구명+재해유형+소재지")은
  우리 districts.json 팝업·우선 확인지역 카드의 단위와 일치
- DCAT 래퍼의 출처·라이선스·기관 = 화면의 **출처 표기**(우리 `official_data`·`source` 표기 자리)

**더 큰 부분** — 표출 항목을 넘어, 이것은 **T3Q 연계가 실제로 어떤 페이로드로 올지의 예고**다.
사건 마스터ID·T코드·법정동코드·passage/filter_meta 구조는 화면 항목이 아니라 **계약**이고,
우리 Adapter(v1.0~v1.1 규칙에서 잡아 둔 Event Master·RefDisasterEventID·taxonomyCodes·
Passage lineage)의 대조 기준이 v0.6 에서 v0.96 으로 올라갔다는 뜻이다.

## 4. 우리가 반영해야 할 사항

### 즉시 확인 (계약 대조 — 코드 변경 없이 가능)

1. **사건ID 형식 대조.** 우리 시드는 `EVT::YYYYMMDD-TYPE-REGION5-SEQ3`
   (`EVT::20100901-TYPH-41430-001`), 정의서 확정 형식은 `KDSA-YYYYMMDD-법정동10-SEQ3`.
   유형코드 유무·행정코드 자릿수(5 vs 10)가 다르다. **Adapter 에 양방향 매핑 규칙을 준비**하고
   `t3q_field_contract_seed` 의 validation 문구에 KDSA 형식을 병기해 둘 것.
   우리 시드의 `legal_region_code_10` 필드가 이미 자리를 잡아 두었다(현재 null) — KDSA 채번의
   법정동 10자리를 받을 자리다.
2. **재난유형 T코드는 이미 정합.** 우리 `taxonomy_codes`(T10105·T10206 등)가 TTAK.KO-10.1047
   그대로다. 유지.
3. **정의서 v0.6 → v0.96 차이 반영.** `메타데이터 참고자료(T3Q)/재난메타_정의서_v0.6` 기준으로
   만든 `t3q_alignment_seed` 의 근거 버전 표기를 갱신하고, 요소ID 참조가 있으면 v0.96 요소마스터
   (372행)와 대조.

### 설계 반영 (다음 개발 사이클)

4. **Passage 계약을 인스턴스 구조에 맞춘다.** T3Q 검색이 돌려줄 원형이
   `passage_text + filter_meta(type_name·class_iri·cq_ids·set_id) + prov(파일·쪽)` 임이
   확인됐다. 우리 `SimilarEvent.evidence`·`t3q_mock_passages_seed` 의 필드에
   `class_iri`·`cq_ids`·`quantity_kind` 를 수용할 자리를 잡아 둘 것(옵션 필드로 — 계약 파괴 없이).
5. **CQ 축과 우리 CQ-01~05 의 대응표.** 이들의 CQ 는 7축(AX-LOC·OBJ·TIME·DEG·ACT·HIST·OUT)
   체계다. 우리 CQ 커버리지 패널(v1.1)에 축 대응 열을 추가하면 T3Q 와 같은 언어로 말하게 된다.
6. **위성 데이터셋 스키마 수용 준비.** /evidence 의 `SatelliteEvidenceSet` 교체(쓰리디랩스) 때
   위성 GEOJSON DATASET v0.8 의 `about_event`·`distribution[]`·AI 패키징 필드를 받을 수 있게
   Adapter 계약을 잡아 둘 것. CCTV 는 POC 범위 밖(고정 범위: CCTV Context 수신 제외)이므로
   규격만 알아 두면 된다.
7. **시간·단위·결측 규약 준수 확인.** 우리 산출물(침수흔적 `collected_at`, 관측 Provider 응답)이
   ISO8601+`+09:00`·null 결측을 이미 따르는지 점검 — 대체로 따르고 있으나 게이트에 명문화할 가치.

### 주의 (하지 말 것)

8. **인스턴스 표본을 실지역 자료처럼 화면에 얹지 않는다.** 표본이 대구(저감계획)·동진강(하천)·
   김해(소하천)로, 우리 대상지역(의왕·구미·남원 / 부산·인제·영천)이 아니다. 쓴다면
   `shared_demo`·`target_region_match=false` 상태를 붙여 참고용으로만.
9. **`schema_version: 3.2 / initial_inferred_schema / review_required: true`.** 이 스키마들은
   문서에서 유도한 초기 추정본이고 요소 바인딩률도 낮다(자연재해저감 65노드 중 bound 16,
   24.6%). **확정 계약으로 간주하지 말 것** — v1.0/v1.1 규칙("외부 API/MCP 미확정, pending 유지")
   그대로 두고, 대표응답이 검증되기 전에는 Adapter 를 실경로로 돌리지 않는다.
10. **문서 원문(PDF/MD)이 이 폴더에 없다.** 메타와 추출 인스턴스만 있다. passage 의
    `source_file` 경로는 T3Q 내부 경로(`C:\T3Q\research\poc2\...`)라 우리가 역참조할 수 없다 —
    근거 표시는 passage_text 와 쪽 번호까지만 가능하다.
